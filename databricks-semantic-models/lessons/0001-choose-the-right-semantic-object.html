Choose the Right Semantic Object

A practical first mental model for Metric Views, Materialized Views, Databricks dashboards, dashboard datasets, and standard views.

Mission tie-in: as a Databricks Data Engineer, your leverage is knowing where business logic, physical optimization, and consumption logic should live. This lesson gives you the first design filter.

Target Skill

Given a reporting or analytics requirement, choose the Databricks object that should own the requirement.

Primary source to read after this lesson: Databricks docs: Unity Catalog metric views. Follow-up source: Metric View tutorial with joins.

The Four Jobs

Metric View

Owns reusable business semantics: fields for grouping/filtering and measures for aggregations. Databricks describes Metric Views as the core implementation of Unity Catalog business semantics. Queries evaluate measures with MEASURE(). Source

Materialized View

Owns physical precomputation: it stores query results, refreshes from source changes or schedules, and can reduce latency and processing cost. Standalone MVs are backed by serverless Lakeflow pipelines. Source

Dashboard

Owns consumption: visualizations, filters, publishing, sharing, scheduling, embedding, and optional Genie exploration. Dashboards define datasets from tables, views, Metric Views, or SQL queries. Source

Standard View

Owns lightweight virtual SQL reuse: no physical data is stored, and metadata changes happen through view DDL. It is not a semantic metric layer and does not precompute results. Source

Key Distinction

Do not ask “Which object can technically produce the chart?” Ask “Which object should own the responsibility?” Business meaning belongs in Metric Views. Performance belongs in Materialized Views. Presentation belongs in dashboards.

Dashboard-local calculations are convenient, but they are a weak place for canonical KPI definitions because they are scoped to one dashboard. Databricks dashboards can export datasets as Metric Views or Materialized Views, which is a hint: local work can be promoted once it becomes reusable. Source

The Production Pattern

A mature Databricks semantic/BI stack often combines the objects instead of choosing only one:

Delta tables
  -> Metric View for governed fields and measures
  -> optional Materialized View or Metric View materialization for latency
  -> AI/BI dashboard for stakeholder consumption
  -> optional Genie for natural-language exploration

Metric View materialization is a special case: it accelerates Metric View queries using materialized views and optimizer query rewriting, but Databricks currently marks this feature experimental. Treat it as an advanced performance topic after you can model Metric Views correctly. Source
