Lesson 0004 - 18 minutes

Use a Metric View in a Dashboard Dataset

Turn the enriched Metric View into a safe AI/BI dashboard dataset, then decide what should stay governed versus dashboard-local.

Mission tie-in: you are moving from semantic modeling into consumption design: the same governed measures must power dashboards and Genie without leaking unnecessary rows or duplicating KPI logic.

Target Skill

By the end, you should be able to choose between direct Metric View selection, a SQL dataset over a Metric View, and a dashboard custom calculation for a concrete dashboard requirement.

Primary source: Databricks docs: Create and manage dashboard datasets. Supporting sources: Query metric views, Dashboard custom calculations, and Genie Spaces with dashboards.

The Consumption Filter

D

Direct Metric View

Select the Unity Catalog Metric View as the dashboard data source when the dashboard can use all defined dimensions and measures. Databricks applies MEASURE() automatically and surfaces agent metadata in the UI.

Q

SQL Dataset

Write a SQL dataset over the Metric View when you need to filter, project, or reshape the result. You must explicitly wrap measures with MEASURE().

C

Custom Calculation

Use a dashboard-scoped calculation for local visualization logic. Databricks notes that reusable custom metrics should be moved to Unity Catalog Metric Views.

Dataset shape is a security boundary for dashboards and Genie: viewers can access dataset results even if a field is not visible in a chart.

Build It

1

Start with the simplest dashboard dataset

In the dashboard Data tab, choose Add data, then select <catalog>.<schema>.orders_customer_metric_view. Databricks says when you choose a Metric View directly, the dataset includes the dimensions and measures defined in the Metric View, and the dashboard can surface display names, formats, and synonyms.

Use this path when the dashboard should expose the full governed semantic model to authors and Genie.

2

Use SQL when you need a restricted dashboard dataset

Databricks recommends avoiding SELECT * and explicitly selecting only required columns, because dashboard viewers and Genie can access dataset query results. A Metric View query must list fields and wrap measures with MEASURE().

SELECT
  market_segment,
  order_status,
  MEASURE(total_revenue) AS total_revenue,
  MEASURE(order_count) AS order_count,
  MEASURE(revenue_per_customer) AS revenue_per_customer
FROM <catalog>.<schema>.orders_customer_metric_view
WHERE order_month >= DATE '1997-01-01'
GROUP BY market_segment, order_status;

This is a dashboard-ready result: no customer names, no raw keys, and only the grain needed for segment/status visuals.

3

Add one local calculation only if it is dashboard-specific

For example, a dashboard-only label that buckets status for a single executive page can stay local as a calculated dimension. But a KPI like gross_margin, net_revenue, or customer_lifetime_value should be promoted into the Metric View if other dashboards, SQL users, or Genie should share it.

CASE
  WHEN order_status = 'Open' THEN 'Active'
  ELSE 'Closed'
END

The Genie Safety Check

Good dataset

Contains only market_segment, order_status, and governed measures. Genie can answer "sales by segment" without seeing customer names or raw keys.

Risky dataset

Contains customer_name, comments, raw identifiers, or extra rows not shown in charts. Databricks warns Genie answers from the full dataset query results, not just visible visualizations.
