Lesson 0005 - 18 minutes

Choose the Freshness and Performance Lever

When a Databricks AI/BI dashboard is slow or stale, pick the smallest lever that fixes the actual bottleneck.

Mission tie-in: you already know Databricks engineering mechanics. This lesson focuses on the semantic and BI layer: turning governed metrics into dashboard experiences with predictable freshness, latency, and cost.

Target Skill

By the end, you should be able to read a dashboard performance symptom and choose between dashboard cache, dashboard schedule, standalone Materialized View, and Metric View materialization.

Primary source: Databricks docs: Dataset optimization and caching. Supporting sources: Use standalone materialized views, CREATE MATERIALIZED VIEW, and Materialization for metric views.

The Four-Lever Model

C

Cache

Databricks dashboards maintain a best-effort 24-hour result cache. It improves load time, but can return stale dashboard results.

S

Schedule

A dashboard schedule runs dataset SQL on an interval and populates cache. Databricks says this can significantly speed initial load for published dashboards with shared permissions.

M

Materialized View

A standalone Materialized View physically stores query results and refreshes manually, on a schedule, or with TRIGGER ON UPDATE. Use it when the dataset query itself is expensive.

V

Metric View Materialization

Metric View materialization is experimental. It precomputes selected Metric View aggregations and lets the optimizer use aggregate-aware query rewriting when eligible.

Do not start by materializing. First decide whether the pain is viewer load, dataset size, source-query cost, or repeated Metric View aggregation patterns.

Diagnose Before You Optimize

1

Check whether dashboard processing is browser-side or backend-side

Databricks dashboards can process filtering and aggregation in the browser when a dataset is small: no more than 100K rows and no more than 100MB. Larger datasets push filtering and aggregation to the backend, and those queries appear in query history.

Dataset
Behavior
Small
Up to 100K rows and 100MB: filtering and aggregation can run in the browser.
Large
Over 100K rows or 100MB: visualization work goes to the backend.
2

Separate dashboard cache from query result cache

Databricks dashboards check the dashboard cache first, then the generic query result cache. The dashboard cache can return stale results for up to 24 hours. The generic query result cache does not return stale data; it is invalidated when underlying data changes.

That means a slow dashboard is not automatically a source-table problem, and a stale dashboard is not automatically a failed pipeline problem.

3

Only then choose a physical optimization

If the dashboard dataset query is expensive every time it runs, use a standalone Materialized View or Metric View materialization. A standalone MV is a general physical result for a query. Metric View materialization keeps the governed metric interface and lets query rewrite choose a matching materialization.

Build the Smallest Fix

Standalone MV for dashboard-ready aggregates

Use this when the dashboard repeatedly needs the same expensive aggregate result, and semantic reuse is less important than a simple physical serving table.

CREATE OR REPLACE MATERIALIZED VIEW sales_daily_mv
  SCHEDULE EVERY 1 DAY
AS SELECT
  date_trunc('day', order_time) AS sales_date,
  market_segment,
  sum(revenue) AS total_revenue,
  count(*) AS order_count
FROM prod.sales.orders
GROUP BY sales_date, market_segment;

Metric View materialization for governed measures

Use this when dashboard and SQL users still query the Metric View, but repeated groups deserve precomputation. Include likely filter fields in the materialization.

materialization:
  schedule: every 6 hours
  mode: relaxed
  materialized_views:
    - name: revenue_by_segment
      type: aggregated
      dimensions:
        - market_segment
        - order_month
      measures:
        - total_revenue
        - order_count

Databricks notes that standalone Materialized Views are refreshed by serverless Lakeflow Spark Declarative Pipelines and can refresh incrementally when the source and query structure support it. Metric View materialization is experimental, requires serverless compute, and currently uses mode: relaxed.

Verify the Fix

For dashboard layer fixes, inspect query history before and after scheduling or dataset-size reduction. For Metric View materialization, Databricks says to use EXPLAIN EXTENDED or query profile and look for a materialization leaf node containing __materialization_mat___metric_view.

EXPLAIN EXTENDED
SELECT
  market_segment,
  order_month,
  MEASURE(total_revenue) AS total_revenue
FROM prod.analytics.orders_customer_metric_view
GROUP BY market_segment, order_month;
