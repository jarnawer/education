Reference 0001

Databricks Semantic Objects

A quick decision sheet for choosing between Metric Views, Materialized Views, AI/BI dashboards, dashboard datasets, and standard views.

One-Line Rule

If you are defining business meaning, start with a Metric View. If you are solving physical performance or refresh, use a Materialized View. If you are delivering interactive consumption, build a Dashboard. If you only need SQL reuse, use a standard view.

Decision Matrix

Object
Use When
Avoid When
Metric View
semantic logic
Define governed business metrics once, with fields for grouping/filtering and measures for aggregations. Query measures using MEASURE(). Metric Views are Unity Catalog business semantics.
You only need a faster physical table, or your requirement is a one-off chart with no reusable business definition.
Materialized View
physical cache
Persist query results for lower latency, recurring expensive transformations, dashboard acceleration, incremental refresh, scheduled refresh, or TRIGGER ON UPDATE.
The core problem is KPI consistency or business terminology rather than compute cost or latency.
Metric View Materialization
semantic acceleration
Accelerate a Metric View with precomputed materializations and optimizer query rewriting. This is experimental and uses Lakeflow-managed materialized views.
You need mature production guarantees without validating experimental feature constraints and fallback behavior.
AI/BI Dashboard
consumption surface
Build visual reports, filters, published sharing, scheduled refreshes, embedded consumption, and optional Genie exploration over dashboard datasets.
You are tempted to hide canonical KPI definitions inside dashboard-local calculations instead of a reusable Unity Catalog object.
Dashboard Dataset
dashboard data shape
Shape the rows/columns a dashboard needs from a table, view, Metric View, or SQL query. Keep sensitive fields out because viewers and Genie can access dataset results.
You need a governed metric definition reused outside that dashboard. Export or promote to a Metric View instead.
Standard View
virtual query
Encapsulate SQL logic without storing data. Good for projection, light joins, compatibility, and non-semantic reusable query shapes.
You need flexible runtime measures, metric metadata, natural-language semantics, or physical performance gains.

Decision Flow

Ask: “Will multiple people or tools need the same KPI definition?” If yes, model a Metric View.

Ask: “Is the query expensive, frequently reused, or latency-sensitive?” If yes, add a Materialized View or Metric View materialization.

Ask: “Is the output a stakeholder-facing report or exploration surface?” If yes, build a Dashboard on top.

Ask: “Is this only SQL reuse without semantic or performance requirements?” If yes, keep it as a standard view.

Ask: “Could sensitive rows or columns leak through dashboard datasets or Genie?” If yes, restrict the dataset before publishing.

Common Combinations

Trusted BI Layer

Delta table -> Metric View -> Dashboard

Best when metric consistency matters more than raw speed.

Fast Trusted BI Layer

Delta table -> Metric View -> Materialization -> Dashboard

Best when business metrics are reused and high-traffic dashboard latency matters.

Precomputed Dataset

Delta table -> Materialized View -> Dashboard

Best when the main need is refreshable physical results, not flexible semantic measures.

Light SQL Abstraction

Delta table -> Standard View -> SQL or dashboard

Best when the logic is simple and does not deserve semantic-model ownership.
